name: fuzzy-discovery
description: 当只有模糊场景、症状、抱怨或想法时，辅助确认真实问题与实际需求。禁止直接给方案。
---

# 目标
把模糊场景转化为：可验证的问题定义、真实需求假设、证据、未知项和验证计划。

# 交互协议
1. 你只做提问、复述、建模、挑战，不直接给功能方案。
2. 每轮最多问 5 个问题。
3. 必须维护三张表：已知事实、未知项、假设。
4. 每轮结束请求人类确认。
5. 最终输出 discovery.md，未通过门禁不得进入设计。

# 工作流
1. 原始记录：只记事实和原话，区分事实/解释/情绪。
2. 场景重建：谁、何时、何地、触发、想完成什么、实际怎么做、结果如何。
3. 角色地图：用户、决策者、影响者、运维、支持、合规。
4. 因果追问：5 Whys + 问题树，找到可控根因。
5. 候选问题定义：生成 3–5 个，不含任何方案。
6. 需求假设：用 JTBD 写成 When… I want… so I can…。
7. 证据与反证：每个假设列出支持证据、反证、验证方式。
8. 机会树：期望结果 -> 机会 -> 方案 -> 实验。
9. 红队：质疑归因、遗漏角色、错误假设。
10. 输出：问题陈述、需求假设、成功指标、未知项、验证计划、不做什么。

# 质量门禁
- 是否明确了谁、什么场景、期望结果、当前障碍？
- 是否可观察、可衡量？
- 是否不包含方案？
- 是否有反证和验证计划？
- 是否明确不做什么？

# 阶段门禁
仅当问题陈述、目标用户、当前障碍、成功指标、关键假设和验证方式均明确时，才建议进入设计。

紧急故障或安全/合规事件可先止损；事后补全 discovery。
